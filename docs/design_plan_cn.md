# 01 设计结论与阅读说明

Agent Relay 设计文档与实现计划

版本 1.0 \| 面向产品负责人和实现团队 \| 日期 2026年10月19日 美西时间

本项目是一项非盈利的 Agent
任务互助服务：发布者把任务和预算固定下来，参与者在手机或网页接单，由自己电脑上的客户端调用本地
Agent
执行。贡献者获得平台积分，用于请求别人的帮助，并通过贡献排行榜获得个人作品的展示机会。

建议继续采用中心化网页平台、本地执行客户端与不可提现积分。先把一个真实任务从接单、执行、回传到结算跑通，再扩大到多
Agent
编排和视频生产。平台当前已发布可用原型，但真实供应商账号的完整端到端联调、浏览器交互验收和强隔离仍未完成。

## 本设计的五项决策

1\.
公开任务优先。用户必须有权公开输入与结果；不接收私人账号凭据、保密论文评审材料或未获授权的内部数据。\
2. 任务发布后固定
prompt、输入、模型和检查规则；接单者不能通过产品界面改写。用户控制本机这一事实意味着平台无法保证客户端不被改动。\
3.
积分按已报告的模型消耗结算，失败任务也可能获得积分；不能把积分当成现金或供应商账单。\
4.
验收定义为预先固定的自动检查，不设置发布者任意拒付的环节。内容质量反馈单独记录。\
5.
个人宣传是贡献的奖励：累计收益榜前十展示排名，前三可自愿展示作品；消费积分不影响历史排名。

## 状态标记

已实现表示代码已写入并发布，不表示真实账号链路已验证；待验证表示存在代码或方案但缺少运行证据；规划表示尚未实现。文中的新接口、运行状态、隔离方案和排期均属于规划，不能据此宣称现网已具备。

# 02 产品目标与用户流程

## 用户与价值

发布者包括额度已用完的研究者、需要写文章或制作内容的创作者，以及想验证改进方案的产品开发者。贡献者愿意提供其被允许使用的模型资源，换取将来获得帮助的积分，以及展示自己的研究、产品或开源项目的机会。两种角色可以是同一个人，但不能接自己的任务。

这里转移的是任务执行责任，而不是模型账户、API key 或供应商 token
的所有权。能否使用订阅计划处理第三方任务，需要按执行端和账户方案单独确认。非盈利和风险声明不能替代这个确认。

## 发布流程

选择任务模板 → 填入公开材料和预期交付 → 选择模型与预算 →
查看自动检查规则与失败计费说明 → 确认公开 →
固定任务包并预留积分。规划中加入发布前预检：缺少材料、执行端不兼容、工具能力不足或预算不合理时直接提示。

## 接单流程

电脑安装 Python 客户端和支持的 CLI，完成本地认证 → CLI 做一次小额自测 →
网页生成配对密钥 → 客户端输入密钥并保持在线 → 手机登录同一平台账户 →
看任务详情并接单 → 电脑自动执行、检查、回传 →
积分到账。手机不承担推理，也不会自动唤醒已关机的电脑。

## 展示流程

贡献者填写展示名称、简介、作品名称与 HTTPS
链接，自愿开启公开。累计收入进入前三后，首页展示作品。关闭公开名片后，介绍与作品退出展示，榜单恢复匿名成员名称。排名更新不扣积分，不保证曝光量或转化。

  --------------------------------------------------------------------------------
  **范围**   **第一阶段承诺**                 **暂不承诺**
  ---------- -------------------------------- ------------------------------------
  任务       固定输入与交付要求；一次接一单   无人值守的无限长任务或任意软件操作

  结算       有上限的积分转移和重复回执幂等   真实消耗防伪、跨供应商现金等价

  质量       JSON 或非空检查；明确交付模板    事实正确、论文新颖性、视频质量保证

  资源       已获授权的本地执行端             绕过订阅限制或共享账号

  隐私       清晰公开告知；密钥留本地         执行者无法阅读任务或模型零留存
  --------------------------------------------------------------------------------

## 试点成功标准

建议先招募 10---20
位知情测试者。衡量从首次配对到首单完成的转化、任务等待时间、真实交付可用率、未知用量比例和参与者复用意愿。具体阈值见第
14 节；这些是试点目标，不是已取得的数据。

token 计量解决。

## 现有实现的关键限制

在线状态目前主要来自配对客户端的心跳，不代表指定模型仍有额度或当前任务一定可执行。平台没有把任务固定绑定到具体设备；多个同账户进程仍可能重复调用模型。积分账本幂等不等于推理调用只发生一次。

CLI
使用临时工作目录和部分工具限制，但不构成完整主机隐私隔离。现网某些身份读取也会更新设备
seen；后续应拆分鉴权与显式心跳。GET
任务列表返回大量任务详情，需改为摘要分页和按需读取，避免公开结果增长后拖慢首页。

本地脚本不是签名的桌面安装器。浏览器 QA
与真实供应商端到端验证尚未完成。已有单元测试和构建成功，只能证明部分逻辑与打包可行，不能替代上述验证。

# 05 系统架构与信任边界

## 控制面与执行面

控制面运行在平台：负责身份、任务不可变版本、预算预留、设备注册、运行租约、事件记录、成果索引和积分结算。执行面运行在参与者电脑：负责下载任务、验证版本、在隔离空间运行适配器、收集用量、检查成果和提交回执。手机只通过控制面接单。

  ------------------------------------------------------------------------------------------
  **组件**     **职责**                         **实现取舍**
  ------------ -------------------------------- --------------------------------------------
  Web 与 API   大厅、资料、接单、进度、榜单     沿用 React 与 Vinext；现网 Cloudflare Worker

  交易数据库   任务状态、租约、账本、权限       沿用 D1；结算以事务或数据库约束保证原子性

  对象存储     任务附件、交付文件、检查报告     规划接入 R2；现网没有启用文件存储绑定

  本地 Worker  配对、轮询、隔离运行、回执重试   先稳定 Python 进程，再做桌面界面与更新机制

  适配器层     不同 CLI 的输入、输出与 usage    固定支持版本；缺失用量显式返回 unknown
               归一                             

  编排器       任务拆分、依赖、聚合、父预算     后续增加；独立身份与权限，不使用管理员凭据
  ------------------------------------------------------------------------------------------

## 网络与凭据

客户端主动连接 HTTPS
API，不要求开放用户电脑端口，也无需手机直连电脑。配对密钥只允许读取已分配任务和提交运行状态；模型凭据留在本机，由
CLI
自己读取。服务端存配对密钥摘要，支持轮换和撤销。客户端不上传完整环境变量、认证文件或本机日志。

## 三条不可消除的信任边界

执行者能接触任务明文，也能修改自己的客户端；平台无法仅靠签名证明模型真的运行。任务内容本身不可信，可能诱导
Agent
读取本地文件或滥用工具。平台与模型供应商均可能处理输入数据，因此公开
Alpha 不能被描述成端到端保密计算。

## 扩展策略

先使用 HTTPS 轮询和数据库租约，达到实际容量瓶颈后再引入队列。长推理不在
Worker 请求内执行；API
只接收小事件和元数据。跨数据库与对象存储没有天然原子性，采用暂存上传、校验摘要、数据库提交索引、定期清理孤儿对象的流程。

# 06 任务协议与主 Agent 编排

## 任务包版本二的建议结构

采用版本化 JSON manifest
加可选文件清单。所有影响执行和计费的字段进入摘要；明确 UTF 8
编码与规范化规则。现网是对保存的原始 payload 字符串做 SHA
256，不是通用跨语言规范化协议，迁移时必须保留 version 1 的验证方式。

  --------------------------------------------------------------------------------------
  **字段组**   **建议字段与约束**
  ------------ -------------------------------------------------------------------------
  身份与版本   task_id、schema_version、template_version、spec_hash、publisher_id

  任务内容     category、prompt、input_manifest、deliverable_schema、public_consent

  能力与权限   adapter、model、required_tools、network_allowlist、execution_profile

  预算与截止   reward_cap_milli、generation_cap、validation_cap、deadline、max_runtime

  验收策略     validator_id、validator_version、rubric_hash、failure_payment_policy

  结果与用量   run_id、artifact_manifest、usage_items、usage_status、check_report
  --------------------------------------------------------------------------------------

## 固定 prompt 的实际含义

平台界面不能编辑已发布任务，接单方不能自行切换模型或规则。CLI
仍有自己的系统指令、版本、默认推理设置和允许的环境差异。要获得可比运行，需要同时固定适配器版本、模型、工具许可和执行配置。摘要只证明任务包字节一致，不证明主机执行过程可信。

## 主 Agent 与平台 Agent

主 Agent
可以代表发布者创建子任务，必须使用有范围限制的机器凭据。权限分为草拟、发布和预算上限；第一次授权绑定具体账户和限额。平台
Agent
发布的任务同样必须有可追溯的付款账户，不得凭空增发积分。该能力目前未实现。

父任务先预留总预算，拆分时把预留额度分配到子任务，而不是重复预留两次。父预算必须满足：子任务额度总和＋聚合和验证额度不超过父预算。每个子任务只结算一次；聚合是独立运行并有独立额度，子任务失败不能无上限自动重试。

任务图默认限制深度 2、最多 5
个子任务，均为建议初值。先有依赖关系和确定交付接口，再允许并行。发布者不得在接单后修改输入；需要变更时创建新版本和新的明确授权，旧运行继续按原版本处理。

# 07 运行状态与故障恢复

## 现有状态与下一版拆分

现网任务状态为 open、claimed、done、failed、cancelled，执行心跳约 20
秒、空闲轮询约 8 秒，90 秒未见设备活动时不允许接单，30
分钟失联可由任务双方关闭。单次模型调用超时约 10
分钟。以上是当前实现参数，不是服务等级承诺。

下一版把任务状态与运行状态分开。任务描述供需关系；run
描述某一次尝试。任务可有多次显式授权尝试，但同一时刻最多一个活跃
run。run 建议采用
assigned、running、uploading、validating、settled、failed、expired。

## 租约与唯一执行权

接单时原子写入 task_id、device_id、run_id、lease_until 与递增
fencing_token。只有持有当前 token
的设备可以续租或提交状态。启动前必须成功取得运行权。租约过期不直接自动重新推理，先标记待处理；若旧运行可能仍在供应商端执行，重复尝试必须提示成本风险并重新授权。

  -------------------------------------------------------------------------------------
  **故障**           **当前行为或风险**        **规划处理**
  ------------------ ------------------------- ----------------------------------------
  两台设备同时运行   结算幂等但推理可能重复    绑定单设备租约；旧 token 不得推进状态

  调用后网络中断     本地保存回执后重试上传    持久化运行日志；回执唯一键 run_id

  调用中崩溃         用量未知，按零结算        先恢复回执；不自动重做付费调用

  用户取消           当前只能取消未接单任务    执行中仅请求停止；已发生用量按规则结算

  超时后晚回执       已关闭任务不重新结算      保存为晚到证据，走显式修正或拒绝策略

  上传中断           当前只有文本结果          分片或断点续传；提交前验证摘要与完整性
  -------------------------------------------------------------------------------------

## 客户端的发布要求

增加单实例锁、明确的就绪状态、自动重连退避、可取消运行和诊断导出。日志默认只记录错误类别、版本和任务
ID。安装包要有版本、校验值、更新签名与回滚机制；自动更新不能静默改变已领取任务的执行配置。

# 08 积分会计与成本边界

## 当前结算规则

1 RP 等于 1,000 milli RP。每个输入 token 计 1 milli RP，每个输出 token
计 3 milli RP。积分费用 C＝min（任务预算 B，输入 token 数＋3×输出 token
数）。全程使用整数。该费率是平台规则，不能解释为跨模型真实成本换算。

账户初始余额为 0，信用额度为 20
RP。发布需同时满足余额非负，以及余额－已预留预算＋信用额度≥新任务预算；当前单任务预算为
1---100
RP。发布时预留预算，结算时释放全部预留，实际费用由发布者转给执行者。余额为负不能继续发布，但可以接单。

例：A 余额 0、预留 0、信用 20 RP，发布预算 10 RP。执行消耗 2,000 输入和
1,000 输出 token，费用 5 RP。结算后 A 余额 −5 RP，执行者增加 5
RP，预留归零。A 必须先接单赚回非负余额才能再次发布。

## 账本不变量

每次非零结算必须同时写入等额借记与贷记；全平台账本净变化为零；任务实际费用不超过预留；预留不为负；重复回执不能追加收入。信用额度是允许欠款的边界，不是赠送的余额，也不计入排行榜。冲正应追加反向分录，不修改历史分录。

## 验证费用与失败成本

建议把"执行者承担验证成本"解释为：执行和验证均由接单方的资源支付，平台不代付；如果验证调用模型，其用量按预先声明的规则计入同一个发布者积分预算。这样验证不是隐藏的额外任务。若希望验证消耗不给积分，应另设显式策略并在接单前展示，不能事后扣除。当前格式检查没有模型用量。

已知用量的失败任务仍按规则结算；缺失用量、超时或崩溃不能估算成真实用量，记录
unknown
并按零处理。应区分零消耗与未知消耗，展示给双方。预算耗尽必须停止新调用，但无法保证中断已经开始的供应商请求。

## 非 token 成本

视频、语音、图像、搜索和存储可能按秒、张、请求或容量计费。第一阶段不纳入纯
token 积分计算；后续增加 usage_items
和独立费率表，发布时固定版本。外部费用仍由执行方承担，积分奖励上限不构成真实现金账单上限。

# 09 排行榜与个人宣传激励

## 现网规则

累计收获为已结算任务的正向收入之和，包含失败任务已知用量的结算，不包含初始信用、消费或未结算预留。排行榜展示前
10
名；前三且开启公开名片的用户展示作品。前三有人未公开时，当前实现留空，不顺延给第四名。

同分按最近一笔收入的时间先后，再按账户标识排序。名片包含名称、180
字以内介绍、作品名称和 HTTPS
链接。用户可随时关闭公开。排名约随页面轮询更新，不承诺实时曝光；作品链接不等于平台背书。

## 激励上的根本冲突

按消耗付酬会让更长输入、更多推理或失败重试产生更多积分；它奖励资源投入，不直接奖励交付价值。加入首页宣传之后，积分具有曝光收益，攻击者更有动力伪报用量、互相发布无意义任务，或利用新账户信用制造排名。双向账本守恒不能防止两个账户反复循环积累总收入。

## 建议的下一版规则

保留"累计赚取积分"作为公开事实指标，同时增加独立的"本期展示资格"。展示资格可要求格式验收通过、至少来自多个不同发布者、近期没有异常和主动公开资料。失败任务继续按既定规则支付，但不必自动带来更多曝光。此项改变属于产品决策，需要公布生效日期，不能回写历史积分。

试点可限制每对账户在一个周期内的展示计分、每日曝光积分上限，以及新账户的信用任务数量。触发异常先暂停推荐位并允许申诉，不直接扣除既得积分。设备或网络信号只能辅助识别，不以同
IP 直接判作弊。上述措施均未实现。

## 运营边界与衡量

首页展示研究、开源项目、产品或个人网站；提供举报、暂停推荐位、链接失效处理和内容下架能力。不要从任务成果自动推断作者身份、版权或允许宣传。每次名片公开与关闭应记录版本和时间。

衡量推荐卡片曝光、外链点击、贡献者回访和实际完成任务数量。避免把点击率直接纳入积分，否则会鼓励夸张宣传。后续可增加滚动月榜，让新参与者有机会；它与累计榜并存而不是删除历史贡献。

Agent 子进程。

## 平台与内容安全

HTTPS，不抓取用户任意 URL 的服务器内网地址。

当前公开任务一旦被第三方读取，删除页面不能保证收回副本。后续如增加私密模式，需要单独设计访问控制、保存期限、删除流程和执行者可见范围，不把加密传输包装成对执行者保密。

5%。用户评价的交付可用率单独报告，建议目标 70%
以上，不因格式通过就自动算有用。样本很小时同时报告绝对数量。

# 15 成本容量与持续优化

## 成本模型

平台成本＝请求与数据库操作＋成果存储＋下载流量＋日志与监控＋运营审核；执行者成本＝模型调用＋外部工具＋本地计算和网络。非盈利意味着不抽取商业利润，不意味着平台没有账单或维护工作。建议按月公开运营成本和资源捐赠，不以积分兑付现金。

现网空闲客户端约每 8 秒轮询一次：持续在线的 100 个客户端约产生 108
万次请求每天；1,000 个约产生 1,080 万次。每次读取若顺带写
seen，会放大数据库写入。应改为更慢的空闲轮询、随机退避和独立心跳，再按实际负载决定是否使用队列或长连接。这里是容量算式，不是供应商报价。

下一版任务列表只返回摘要并分页；结果按需加载。排行榜可维护派生聚合或短时缓存，账本仍是事实来源。用户关闭公开名片需要立即清缓存，不能为了性能继续暴露旧内容。大型媒体走对象存储，不进入数据库文本列。

## 为什么统一费率需要审视

不同模型的输入、缓存、输出和推理成本差异很大；用同一 RP
费率不能保证参与者等价交换。第一阶段将其明确作为社区贡献单位。后续若需要多费率，发布者选择并固定计量规则，展示预计积分和已知成本范围，不把供应商当前价格硬编码进任务。

## 持续优化工具的定位

可以增加离线优化循环：收集脱敏失败类型 → 构建固定评测集 →
生成模板或代码候选 → 在隔离环境评测 → 比较质量、成本和安全 → 人工审阅 →
发布新模板版本。优化只能影响新任务，不能修改已发布
prompt、费率或验收规则。

评价至少同时考虑正确性、可用性、消耗、延迟和违规工具调用。独立留出测试集，防止只优化已知题目。主
Agent
可建议改进，但不能自行更改平台权限、增发积分或部署生产。先用现有测试与版本管理形成反馈循环，再决定是否接入专门的自动优化框架。

## 停止或转向的证据

如果合法可用资源稀缺、参与者安装成本过高、任务长期无人接、未知计量过多或结果没有实际价值，应缩小到一个社区和一种任务类型。若
API
成本无法带来比直接购买更好的体验，产品价值应转向协作与个人展示，而非继续宣称节省闲置订阅额度。

# 16 决策记录与参考依据

## 与 ERC 8414 的关系

ERC 8414
的作者提案讨论把任务文档、版本、验收主体和悬赏绑定起来，并强调已提交成果与取消退款之间的关系。本项目借鉴"先固定任务与规则，再提交结果"的思想；第一阶段不用
NFT、钱包或链上托管，不宣称兼容该接口。链上提交摘要也不能自动证明本机消耗和内容质量。\[S4\]

本平台允许信用余额为负，采用按已知消耗结算，这与资金预先充足并按接受成果支付的悬赏契约有明显差异。以后若加入链上模式，应作为独立结算后端和任务类型，不在原积分账户上直接套用。提案内容可能变化，采用前应固定具体版本并重新评审。
